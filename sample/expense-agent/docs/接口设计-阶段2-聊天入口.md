## 0. 三个前置约定

1. **先定协议再写代码**：SSE 的事件类型一旦定错（尤其"来源什么时候推"），前端要返工。
2. **错误信息一律中文且可直接展示给用户**，同时带 `request_id` 便于查日志；内部异常不外泄堆栈。
3. **历史消息只用于上下文消解，不作为回答依据**。答案依据只能是本次检索到的制度原文——这是需求评审定的红线，协议设计必须配合（见 §5）。

## 1. 统一响应约定

所有**非流式**接口返回统一信封：

```json
{ "code": 0, "message": "成功", "data": { }, "request_id": "req_01HQ..." }
```

- `code = 0` 成功；非 0 见 §8 错误码表。
- HTTP 状态码只表达"传输层"语义，业务结果看 `code`：

| HTTP | 场景 |
|---|---|
| 200 | 业务成功 |
| 400 | 参数错误（code 10xx） |
| 401 | 未登录 / token 失效（1101） |
| 403 | 越权访问他人会话（1102） |
| 404 | 会话不存在（2001） |
| 429 | 触发限流（1201） |
| 500 | 服务内部错误（5000） |
| 502 | 上游模型不可用（4001/4002） |

## 2. SSE 流式协议（**最需要你先确认的部分**）

`POST /api/v1/chat`，`Content-Type: text/event-stream; charset=utf-8`。

### 事件时序

```
event: meta      → 先建 assistant 占位消息，把 message_id 交给前端（断线也能对账）
event: status    → {"stage":"retrieving","text":"正在检索制度…"}
event: sources   → 检索到的条文来源（生成前推，前端可先把"依据"渲染出来）
event: status    → {"stage":"generating","text":"正在生成回答…"}
event: delta     → {"content":"北京属…"}     （多次，逐块）
event: done      → {"message_id":..,"finish_reason":"stop","usage":{..},"latency_ms":..}
data: [DONE]
```

异常路径：`event: error → {"code":4001,"message":"模型服务暂时不可用，请稍后重试"}` 后关闭流。
心跳：每 15 秒发一行注释 `: ping`，防止反向代理掐断长连接。

### 事件定义

| event | data 结构 | 时机 |
|---|---|---|
| `meta` | `{message_id, session_id, created_at}` | 建占位消息后立即 |
| `status` | `{stage, text}` | `retrieving` / `generating` / `rewriting` |
| `sources` | `{sources:[{no, chunk_id, file, clause_no, heading_path, snippet, score, low_confidence}]}` | 检索完成 |
| `delta` | `{content}` | 模型流式输出 |
| `done` | `{message_id, finish_reason, usage:{prompt_tokens,completion_tokens}, latency_ms}` | 正常结束 |
| `error` | `{code, message}` | 任意阶段失败 |

### 两条关键设计

- **先落库占位消息再流式**：用户刷新/断网时，已生成的部分照样写进库（标记 `finish_reason=aborted`），回来能看到半截答案而不是一片空白。
- **`sources` 在 `delta` 之前推**：让"依据"先于"结论"出现，用户能边看答案边核对条款，也更符合审计直觉。

## 3. 接口清单

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/v1/chat` | SSE 流式问答（本期核心） |
| POST | `/api/v1/sessions` | 新建会话，返回 `session_id` |
| GET | `/api/v1/sessions` | 会话列表（分页，按最近更新排序） |
| GET | `/api/v1/sessions/{id}/messages` | 历史消息（刷新页面恢复用） |
| DELETE | `/api/v1/sessions/{id}` | 归档会话（软删） |
| GET | `/api/v1/sources/{chunk_id}` | 条文原文详情（前端展开全文用） |
| GET | `/api/v1/health` | 健康检查：DB / 向量库 / 模型连通性 |

> `/chat` 的 `session_id` 可为空：为空时后端自动建会话，并在 `meta` 事件里回传新 `session_id`。

## 4. 请求 / 响应字段

### POST /api/v1/chat

```json
{
  "session_id": "可选的会话ID，为空则自动新建",
  "question": "P3职级去北京出差住宿费标准是多少？",
  "stream": true,
  "top_k": 3
}
```

校验：`question` 必填、trim 后非空、长度 ≤ 1000（超限 1002）；`top_k` 1~8（超限 1001）。

### 会话 / 消息

```json
// POST /api/v1/sessions 响应 data
{ "session_id": "se_xxx", "title": "北京出差住宿标准", "created_at": "2026-10-30T09:30:00Z" }

// GET /api/v1/sessions/{id}/messages 响应 data
{ "items": [
    { "id": "ms_1", "seq": 1, "role": "user", "content": "…", "created_at": "…" },
    { "id": "ms_2", "seq": 2, "role": "assistant", "content": "…",
      "retrieval_refs": [ { "no": 1, "file": "差旅报销制度.md", "clause_no": "3.2.1",
                            "heading_path": "三、差旅标准 > 3.2 住宿费", "snippet": "…" } ],
      "finish_reason": "stop" }
  ], "has_more": false }
```

## 5. 上下文策略（最近 6 轮）

| 规则 | 设计 |
|---|---|
| 轮的定义 | 1 轮 = 1 条 user + 1 条 assistant，**取最近 6 轮 = 最多 12 条** |
| 过滤 | 只取 `role in (user, assistant)`，排除 `system` / `tool` |
| 排序 | 按 `seq` 升序取最后 12 条，再原序拼入 messages |
| 长度兜底 | 估算 token 超 ~2000 时，**从最早开始整轮丢弃**（不截断单条，避免半句话） |
| 携带内容 | 历史只带纯文本；**`retrieval_refs` 不重复注入**（否则上下文爆炸） |
| 指代消解 | 可选 `rewrite_query`：用 LLM 把"那 P4 呢？"补全成完整问题再检索。**默认关闭**（多一次调用、增加首字延迟），列为 P1 |
| **红线** | 历史上下文只帮助理解指代，**答案依据只能来自本次检索的制度原文**；提示词里明确写死 |

## 6. 检索与来源展示

- 复用阶段1 `hybrid_search`（RRF 融合，默认 top_k=3）。
- 来源字段：`{no, chunk_id, file, clause_no, heading_path, snippet(前 120 字), score, low_confidence}`。
- **低置信度处理**：向量分低于阈值（建议 0.15，接入真实 embedding 后需重新标定）时，仍生成回答但 `low_confidence=true`，前端展示「依据较弱，建议咨询财务部门」横幅。**不直接拒答**——拒答会摧毁用户信任，标弱提示更可控。
- 完全没检索到（0 条）：不调模型，直接返回固定话术「制度中未检到相关规定，建议咨询财务部门」+ code 3002，前端按普通回答渲染。

## 7. 数据落库（SQLite，沿用阶段1）

| 表 | 本期新增/调整字段 |
|---|---|
| `users` | 沿用；原型期用 mock 用户，字段先建好 |
| `sessions` | + `channel`、`model`、`prompt_version`、`message_count`、`token_total`、`context_json`（阶段3 放草稿 id）、`expires_at` |
| `messages` | + `seq`（会话内序号，前端排序稳定）、`retrieval_refs`（JSON）、`model`、`prompt_version`、`latency_ms`、`finish_reason`、`error_text`、`guardrail_hits` |
| `policy_chunks` | 沿用阶段1（SQLite 存文本与元数据；向量仍在 FAISS，chunk_id 对齐） |

**SQLite 工程注意**：
- 开 WAL 模式 + `busy_timeout`，避免 SSE 并发写锁冲突。
- 流式期间**不持有长事务**：先 insert 占位 → 提交 → 流式过程中分批 update → 结束再 update 一次。
- 原型阶段够用；正式并发（>50 并发写）建议换 PostgreSQL——这条我会写在代码注释里，不做隐藏假设。

| code | HTTP | 中文提示（可直接展示） |
|---|---|---|
| 0 | 200 | 成功 |
| 1001 | 400 | 请求参数不完整或格式不正确 |
| 1002 | 400 | 问题内容过长，请精简至 1000 字以内 |
| 1003 | 400 | 请求格式无法解析 |
| 1101 | 401 | 登录状态已失效，请重新登录 |
| 1102 | 403 | 无权访问该会话 |
| 1201 | 429 | 操作过于频繁，请稍后再试 |
| 2001 | 404 | 会话不存在或已被删除 |
| 2002 | 400 | 会话已归档，无法继续提问 |
| 3001 | 500 | 制度知识库尚未初始化，请联系管理员上传制度文档 |
| 3002 | 200 | 未在制度中检索到相关规定，建议咨询财务部门 |

| 4002 | 502 | 模型响应超时，请重试 |

> 约定：3002 / 4003 属于"业务性结果"，HTTP 仍返回 200，前端按普通消息渲染，不弹错误框。

## 9. 前端设计（单页 HTML + 原生 JS）

### 布局
左：会话列表（P1，本期可先只保留"新会话"按钮）｜中：消息流｜底：输入框 + 停止按钮。

### 状态机
`idle → sending`(显示"正在检索制度…") `→ streaming`(显示"正在生成回答…") `→ done / error`

### 关键实现点
1. **SSE 用 `fetch + ReadableStream` 手动解析**（`EventSource` 不支持 POST）；按 `\n\n` 切事件，取 `event:` 与 `data:` 行。
2. **打字机效果**：`delta` 到达即 append 到 DOM 文本节点；若模型不支持流式，退化为"拿到全文后按 20ms/字渲染"。
3. **来源区**：回答底部渲染来源卡片（文件名 + 条款号 + 章节路径 + 片段），点击展开全文（调 `/sources/{chunk_id}`）；正文中的 `[1][2]` 与卡片编号对应。
4. **停止生成**：`AbortController.abort()`，后端检测到断连即 finalize 已生成内容。
5. **刷新恢复**：刷新后用 `GET /sessions/{id}/messages` 重建消息流。
6. **XSS 防护**：制度原文与模型输出一律用 `textContent` 渲染；若要支持 Markdown，必须 `marked` + `DOMPurify` 净化后再插入。

### 验收清单
- [ ] 提问后 1 秒内出现"正在检索制度…"，随后切换为"正在生成回答…"
- [ ] 回答逐字流出，可点"停止"中断，中断后已生成内容仍保留
- [ ] 回答底部显示 3 条来源（文件名 + 条款号 + 片段），点击可展开原文
- [ ] 断网 / 模型 502 时显示中文错误提示 + request_id，不白屏
- [ ] 刷新页面后历史消息完整恢复
- [ ] 追问"那 P4 呢？"能正确指代上一轮问题（依赖 §5 的消解开关）

## 10. 需要你拍板的 6 个决策点

| # | 决策 | 我的建议 |
|---|---|---|
| 1 | `sources` 在生成**前**推还是生成**后**推？ | **前推**：依据先于结论，用户可边看边核对 |
| 2 | 是否开启多轮指代消解 `rewrite_query`？ | 一期**关闭**（多一次 LLM 调用，首字延迟 +1~2s），二期按准确率数据决定 |
| 3 | 客户端断连时是否仍落库已生成内容？ | **是**，标记 `finish_reason=aborted`，避免用户丢答案 |
| 4 | 检索置信度低时：仍回答 + 弱提示，还是直接拒答？ | **仍回答 + 弱提示**，拒答伤信任 |
| 5 | SQLite 撑并发够不够？ | 原型够；并发 >50 或要上生产就换 PostgreSQL（我会在代码里标注切换点） |
| 6 | 本期是否做会话列表侧栏与"停止生成"按钮？ | **都做**，工作量约半天，但决定可用性 |
